- **There are TWO committed reference schema dumps — use the right one per backend, and any PR that adds/edits/removes a migration MUST regenerate BOTH in the same PR.** `migrations/schema.sql` is the **PostgreSQL** dump; `migrations/schema.sqlite.sql` is the **SQLite** dump (SQLite is what local dev and the Vitest tests use). The dialects differ (`character varying`/`jsonb`/`timestamp with time zone` vs `varchar`/`json`/`datetime`), so a PG dump can't load into SQLite — read the file matching the backend. The app runs Knex migrations, but the Vitest suite builds its test databases straight from these dumps (`lib/database/testUtils.ts`), so drift breaks or falsifies tests. Regenerate by running all migrations against a **local** DB of each type: Postgres → `pg_dump --schema-only --no-owner --no-privileges` then strip pg_dump chatter (`\restrict`/`\unrestrict`, `-- …` comments, `SET default_tablespace`/`default_table_access_method`); SQLite → `sqlite3 file .schema` then strip auto-managed internal tables (`sqlite_sequence`, FTS5 `*_fts_data/idx/docsize/config/content` shadow tables) while keeping the `CREATE VIRTUAL TABLE … fts5` + triggers. Both files are kept tracked via `!` negations in `.gitignore` (which otherwise ignores `*.sql`). Don't hand-edit or chase old formatting; commit as `none:` if it's the only change. See **Keeping the reference schema dumps in sync** in `AGENTS.md`.
- **"In lockstep" means the same migration set, NOT the same column types — and a client-supplied id compared against a numeric column must be coerced first.** A backend-conditional migration makes the two dumps legitimately disagree: `20260207223000_fix_attachments_media_id_type.js` returns early unless the client is `pg`, so `attachments.mediaId` is `integer` on PostgreSQL and `varchar(255)` on SQLite. That is not drift — check the migration before "reconciling" it or regenerating. The same integer typing is a live bug source: `medias.id` is `integer` on PostgreSQL, so `where('medias.id', 'abc')` raises `invalid input syntax for type integer` and a 404 becomes a 500, while SQLite's dynamic typing simply matches nothing. Every method in `lib/database/sql/media.ts` that **compares** a `mediaId` against `medias.id` runs it through `toMediaRowId` first. The guard is shape-checked and capped at 2147483647, not a bare `Number()`: `Number('0x10')` is 16, so coercing loosely resolves a different row than the id names, and an out-of-range id raises `value out of range for type integer`. It accepts optional leading zeros, digits, an optional all-zero fraction, and 1..2147483647 — nothing else — which is deliberately tighter than the backends: `'0x10'` resolved media 16 on PostgreSQL 16+ and `'+12'`/`' 12 '` resolved media 12 on both, and all now 404. `'12.0'` is kept only because SQLite's `varchar` `attachments.mediaId` can hold that form. `createAttachment` **writes** `mediaId` and is deliberately unguarded; be aware `POST /api/v1/accounts/outbox` reaches it with an unvalidated id, which is a separate open bug. Do the same for any new numeric-column lookup, and give fixtures values the column can actually hold. CI pins `TEST_DATABASE_TYPE=sqlite`, so only a `TEST_DATABASE_TYPE=pg` run catches this class. See **Database Compatibility Guidelines** in `AGENTS.md`.
- **The viewer's own follow row is read through `getViewerFollow` (`lib/services/getViewerFollow.ts`) on read paths, and through `database.getAcceptedOrRequestedFollow` everywhere else.** A signed-in non-owner's `/@user@domain` asks for that one row from two places that cannot see each other — `resolveActorStatusesAudience`, deciding whether followers-only posts are in scope, and `getRelationship`, for the follow button plus its reblog/notify preferences and language filter — so the helper wraps it in React `cache` and the two collapse into one query. Its arguments are **positional** because `cache` keys on argument identity; the options-object spelling the database method uses would allocate a fresh key per call and memoize nothing. **Read paths only** — follow, unfollow, block and follow-request authorize/reject read the row, mutate it, then report the result through `getRelationship`, reaching the helper only after their own write; routing one of their pre-mutation reads through it would describe the state they just replaced. `canActorReadSingleStatus` stays direct as a SCOPE boundary, not because it never repeats — two boosts of the same followers-only author on one profile do repeat it; routing it through the helper is safe but reaches a dozen further call sites, so it is its own change. Note React `cache` is a **passthrough** under Vitest — a test needs `runInReactCacheScope` (`@/lib/testing/reactCacheScope`) or it asserts nothing. See **Who May See an Actor's Statuses** and **Testing Guidelines** in `AGENTS.md`.
- **"Is this actor local?" is `whereLocalActor` (`lib/database/sql/utils/localActor.ts`) = `privateKey IS NOT NULL AND privateKey <> ''` — never a hand-written null check, and in JS `Boolean(actor.privateKey)`, never `actor.privateKey !== ''`.** Legacy rows store `''` for REMOTE actors, so a null-only SQL check called 216 of 221 production rows local and served a majority-remote "local" timeline; the JS form is worse than wrong, it is inert, because the row mapper omits `privateKey` when falsy so the field is a real key or `undefined` and never `''` — that let `addStatusToTimelines` fan every status out to remote recipients. `.modify()` returns `QueryBuilder<any, any>`, so name the row type on the `select` (`.select<SQLActor[]>('*')`) where the rows are consumed typed. The **local public timeline additionally must not join `actors`** — it passes the ids in as literal values, because joining that unique key collapses the planner's estimate and, once the `<> ''` predicate is present, loses `LIMIT` early termination at every page size (on a local seed matching production's shape, 176 buffers vs ~16,700 at a page of 30) — so the correctness fix alone would have made this query dramatically worse. See **Local Actors** in `AGENTS.md`.
- **Order a composite index so the columns EVERY caller constrains come first, and do not chase PostgreSQL 18 picking an index whose leading column your query leaves free.** `statuses_announce_original_actor_idx` is `(type, "originalStatusId", "actorId")` because `getRebloggedBy` pins `type` and `originalStatusId` and leaves `actorId` free; with `actorId` in the middle it could not use `originalStatusId` as an index condition and `GET /api/v1/statuses/:id/reblogged_by` bitmap-scanned every Announce row — 8,973 buffers / 18.4 ms on production to return 1 row. The other four announce callers pin all three columns, so the order is invisible to them and to every result-based test: `statusAnnounceIndexOrderMigration.test.ts` reads the index definition for that reason. Separately, PG 18's B-tree skip scan lets the planner pick a `type`-led index for an `actorId`-only predicate, because `cost_index` prices heap I/O off the LEADING column's correlation and a low-cardinality column scores high spuriously (production: `type` 0.787, `actorId` -0.181). That was investigated twice before anyone measured it, and it is worth ~5% of buffers — the heap fetches dominate and are identical either way — so it is not a bug to fix. There is **no `enable_indexskipscan` GUC**, and never A/B it by dropping an index on production (ACCESS EXCLUSIVE lock, even inside a rolled-back transaction). `statuses_actorId_idx` stays: it is what the owner profile timeline scans backward with `Index Searches: 1` and early termination (29 buffers, vs 693 without), and production has scanned it 3.8M times. See **Composite Index Column Order on `statuses`** in `AGENTS.md`.
- **"Is this status publicly readable?" has TWO forms and the choice is measured: `wherePubliclyReadableStatus` (correlated, `lib/database/sql/utils/publiclyReadableStatus.ts`) wherever a LIMIT bounds the rows, `buildPubliclyReadableStatusIdsQuery` (set-based) only where a COUNT must touch every one.** The set form materialises the actor's whole public history before `LIMIT` sees a row, which is why the signed-out profile page sat at ~33,310 buffers for any page size on a production-shaped PostgreSQL 18 seed, against 476 correlated. `getActorStatusesCount` AND `getRebloggedBy` deliberately keep the set form — the correlated one costs a recursive-CTE instantiation per Announce, which a COUNT cannot amortise (54ms vs 18ms), and `getRebloggedBy` embeds its filtered set twice (FROM subquery + correlated `whereNotExists` dedupe) so it re-evaluates per row PAIR (415ms vs 33ms, shipped correlated and caught in review) — so do not "finish the unification". Being unlimited is not disqualifying on its own: `getStatusRepliesCount` is an unbounded COUNT on the correlated form because one status's replies are a small set; what costs is the number of evaluations. Never add a depth-1 fast-path `EXISTS` beside the chain: PostgreSQL decorrelates it into a hashed SubPlan over every non-Announce status in the instance (476 buffers → 11,294). Both spellings share `announceOriginalPointer`, `publiclyReadableStatusEquivalence.test.ts` proves they agree, and `publiclyReadableStatusQueryShape.test.ts` is the ONLY thing that catches a revert — every result-based test passes against the slow form. **The count still cannot be a counter but IS cached for 60s, and the cache holds the PROMISE**: the outbox root reads `totalItems` through `getCachedActorPublicStatusesCount` (`lib/services/statuses/actorPublicStatusesCount.ts`, bounded `WeakMap<Database, Map<actorId, …>>`, errors never cached) and sends `Cache-Control: public, max-age=60, s-maxage=60` — after 530 root fetches in 11 minutes queued on a 1-vCPU instance and took a ~150ms query to a 899ms average. **Caching the promise, not the count, is what collapses concurrent misses** (same pattern as `getMySQLFullTextMinTokenSize` in `lib/database/sql/search/documents.ts`) — don't "simplify" it back to a resolved value: a shared cache keying on per-request headers like `Signature`/`Date` collapses signed federation fetches into nothing, so the origin must survive a burst alone. Cache-Control on the **root only**; `?page=true` sends explicit `no-store` (live per-status visibility), and the root `Vary`s on the host headers that pick the actor plus `Origin`. See **Publicly Readable Status Ids** in `AGENTS.md`.

- **A route heatmap tile build folds each activity exactly once, and every rule
  around it exists for that.** Tile visit counts ACCUMULATE, so a double fold is
  a permanently wrong number that nothing downstream can detect — unlike a
  missing tile. The fold gate is POSITIONAL (`(createdAt, id)` against the
  build's own cursor, scanning descending), never a counter; the cursor advances
  for every file the pass finished with, including one whose download threw,
  which is why it lives in a `finally`. Resuming requires presenting the build's
  own token (row id + `claimSeq`) — `resume: true` is not that — and a pass that
  can present neither a token nor an offset of zero must not CLAIM at all,
  because the claim's compare-and-swap is destructive. Every fence names the
  pyramid ROW as well as the token, the claim's CAS and the read confirming it
  share one transaction, and any tile-path failure abandons the build rather
  than failing the legacy heatmap the user can actually see. A build only
  completes over a history it actually scanned, and one that could not READ
  every file completes but records the loss on the row. **Tiles are stored
  UNCLIPPED and a region is applied when they are SERVED**, which makes the
  public token route's clipping a security boundary rather than a view option:
  the region comes from the shared row, never the caller; out-of-region tiles
  are settled before any read; and the resolver FAILS CLOSED, because
  `getRegionBounds` answers `[]` for an unparseable region as well as for the
  world, and `[]` means "clip nothing". **All four PUBLIC surfaces** (share page,
  embed page, embed image, embed tiles — NOT the owner tile route, which clips
  to its own authenticated caller's region) refuse such a row through the one
  `resolveSharedHeatmapRegionBounds` — the untiled geometry was built unclipped
  too — and anything PRODUCING a rectangle gates on
  `isSerializableRect`, the rule `serializeRegions` itself applies, since a box
  thinner than the 0.01° step is well formed yet has no canonical key of its own
  and would take the WORLD's key. Only a `completed` pyramid serves tiles
  and only at its own `version`; the public path re-encodes every byte it
  returns and strips the privacy flag while keeping the geometry; and a
  well-formed `v` busts caches without ever filtering tiles (a malformed one is
  a 400 on both routes). The public route also REFUSES any share the pyramid
  cannot answer, through the same `buildHeatmapTileSource` that decides whether
  a heatmap advertises tiles — a share scoped to one sport or one year would
  otherwise be served the actor's whole history, which clipping cannot catch. See **Fitness Route
  Heatmap Pyramid** in `AGENTS.md`.

Both therefore drive the shared `useInlineComposer`/`InlineStatusComposer` themselves, passing `editable` + `onEdit` + `onQuote` — that is the shared layer doing the wiring, not a page opting into per-status callbacks. A surface may also **add** a `⋯` item for something only it knows about the post, via `Actions`' `extraMenuItems` (the fitness detail's "Change gear" submenu is the only one); there is deliberately no way to remove or replace one of the menu's own items. See **Status Posts & Actions** in `AGENTS.md`.
- **A status's media is one attachment at its own size, or a horizontally scrollable strip — never a grid.** `lib/components/posts/attachments.tsx` owns this for every post surface. A lone picture keeps its own aspect ratio and hugs the post's left edge, scaled by **width** (`min(100%, round(SINGLE_MAX_HEIGHT * ratio)px)`, capped at the file's own pixels) — never by capping the height of an `aspect-ratio` box, which leaves the ratio to be re-derived from a clamped axis and resolves inconsistently across browsers; the branch this replaced cropped every portrait photo to a full-width 16:9. Two or more become a fixed-height row whose details are load-bearing: `STRIP_ITEM_MAX_WIDTH` (78%) so the next item always peeks — that peek is what says "this scrolls" on a touch screen, where the back chevron never appears at all — `flex-none` so the items overflow instead of shrinking to fit (drop it and the whole feature silently turns off), `x proximity` snapping, never `mandatory` (which pulls the peek flush the moment the scroll settles), and a back chevron that appears only on hover and is `pointer-events-none` while `opacity-0` (that alone still hit-tests, and `group-hover` never latches on touch, leaving a dead column over the leftmost photo). Keeping the chevrons out of the tab order takes **both** `tabIndex={-1}` and a mousedown guard — `tabindex="-1"` removes an element from the SEQUENTIAL order only, and Chrome and Firefox focus a button on click, so without the guard a chevron unmounted by its own scroll drops focus to `<body>`. A strip item's focus indicator is an **`outline` with a negative offset**: an outset ring is clipped by the strip's `overflow-x-auto`, and an inset ring is invisible because an inset `box-shadow` paints beneath the opaque image. There is **no 4-item cap and no `+N` overlay** (scrolling reaches everything), so strip images pass `loading="lazy"` and strip videos `preload="none"` (`loading` is image-only) — but **only a video carrying a `poster`**, because a posterless one's sole pre-playback frame comes from the `#t=0.01` source fragment, which needs metadata to decode, so deferring one leaves a bare empty box, and federated video never has a poster (`thumbnailUrl` is written on the local-upload path alone) — while a lone picture or video stays eager, an in-viewport lazy image being fetched at lower priority, wrong for the post's largest element. The edge fade is a **`mask-image`** (in `buildEdgeFadeMask`, because jsdom's CSS parser drops a gradient carrying `calc()`), not a background gradient: posts render on four surfaces (`bg-card`, `bg-background`, `bg-muted/30`, unframed) and a fade in one token is wrong on the other three and in dark mode everywhere. `isVisualAttachment` picks what gets a picture box, `isAudibleAttachment` renders audio as left-aligned players below, and a `.fit` file or PDF is skipped rather than rendering the grid's empty box — and the **lightbox is handed exactly the pictures on screen**, indexed into that list, or `MediasModal` shows a blank slide and a wrong "n of m". Anything asking "do I have media" asks `isRenderableAttachment`, not `attachments.length` (`post.tsx`'s link-preview suppression does). Every picture button carries an explicit `aria-label`, since federation writes `attachment.name || ''` and an undescribed photo announced as a bare "button". **A stored `0` means "unknown", not "zero pixels"** — media-storage paths persist `metaData.width ?? 0` — so all dimensions go through `getMediaGeometry`, which also clamps the shape (a 10x10000 sliver otherwise rounds an axis to zero) and falls back to `FALLBACK_ASPECT_RATIO` so blurhash has a box. Affordances come from `useMediaStripScroll` (container-measured, **callback** ref because the strip is conditional), whose `contentKey` must describe item **widths**, not their count. The `no-scrollbar` utility it needs is now defined in `app/globals.css` and belongs **only** on a row with its own overflow affordance — it had been applied in two pickers while defined nowhere, and defining it would have taken away their only cue, so both were switched back to a plain scrollbar. See **Post media layout** in `AGENTS.md`.
- **The reaction chips and the action row are both full-bleed (`-ml-13`), and the action row packs its actions into one `gap-1` cluster at the post's left edge with only the `⋯` menu pushed right by an `ml-auto` on its wrapper** — the auto margin is what does the work (flexbox feeds free space to auto margins **before** `justify-content` sees it, so it beats any `justify-content` the row might carry — the design kit's own row keeps an inert `justify-between` beside it). Drop the margin and `⋯` collapses into the cluster; put `justify-between` on the row without it and all five actions spread across the whole width, reading as five unrelated controls. Each row owns a separate `fullBleed` prop and they default **differently** — `Actions` pulls unless a caller opts out, `ReactionRow` pulls only when asked — and a surface with no avatar column to pull back over ends up with neither (the fitness activity detail's card passes `fullBleed={false}` to `Actions` and simply leaves `ReactionRow`'s own prop unset). The row still spans the **full** width — not for the spacing between actions, which is a width-independent `gap-1`, but so `⋯` lands on the post's right edge and the edit-history panel has that edge to line up with — so never seat it beside something else. The edit-history panel is anchored to the **row** (its trigger's wrapper is deliberately not `relative`) and sits `right-0`, flush with the post's right edge; anchored to the trigger, its 25rem width starts wherever the engagement counts push that trigger and the post's card clips the overhang. The picker trigger lives **in the action row** (`ReactionButton`, `SmilePlus` + total), not beside the chips; both halves share one `useReactionState`. A post narrower than 400px (measured with a `ResizeObserver` on the row, not a viewport breakpoint) moves bookmark and react into the `⋯` menu. **Even a bespoke presentation renders the shared `<Actions>`** — `FitnessStatusDetail` lays out its own card and places the chip row by hand, but its action row is `<Actions>`, not a local copy. See **Status Posts & Actions** in `AGENTS.md`.
- **Three fitness stat strips render through `FitnessStatGrid` (`@/lib/components/fitness/FitnessStatGrid`), and its column rule is a CONTAINER query, not a viewport breakpoint** — the activity detail page's header strip, the strip under its route map, and the inline chip in a timeline post. The gear detail page's strip (still on a `sm:` viewport query) and the fitness overview's totals (`@2xl/fitness`) are **not** migrated yet, so don't read the rule as describing the whole tree. `detail` is 1-up → 2-up at 420px → 4-up at 780px; `chip` is 2-up → 4-up at 424px and never drops to one column. The design system measures each grid's own width for the same reason `useCompactActionBar` does — a strip can sit in a narrow column on a wide window — and the old `sm:grid-cols-4` is exactly what kept four `text-[28px]` tiles in a 565px tablet column, wrapping "31.1 km/h" onto two lines. The detail page's two strips measure separately (the header one is inside the card's `p-5`, 42px narrower) and may differ by one step; that is the rule working. `@container` goes on a wrapper, never on the grid itself. Gear rides inline in the header's metadata line (`date · visibility · gear`) on the detail page and inside the distance cell ("42.6 km · Moots") in the chip. See **Fitness Stat Strips** and **Fitness Gear** in `AGENTS.md`.
- **A fitness post's `createdAt` is NOT the activity's start time — read `fitness_files.activityStartTime`.** A post created through `importFitnessFiles` was backdated to the earliest target activity's start — or, with no parsed start time, to the fitness file row's own `createdAt` — until the Strava webhook opted into `postAtImportTime` (`lib/jobs/importFitnessFilesJob.ts`), which stamps the status when the import publishes it so a just-finished ride is not filed hours down the timeline behind everything posted while it was still being ridden, and does so for ANY activity the webhook delivers however old; every other caller (archive walker, multi-file upload, retry-all, the `scripts/fitness` recovery tools) still backdates, because each replays history. Anything rendering, sorting or grouping by "when the activity happened" must read the FILE, not the post — `FitnessStatusDetail`'s date, the import email's `fitness?.activityStartTime ?? status.createdAt`, and `getActivityImportGroupKey` all do — and `StatusFitnessFile.activityStartTime` exists so a surface holding only a status has it: the detail page's placeholder used `status.createdAt` as a stand-in and started dating rides wrongly the moment those two diverged. The post's own `createdAt` stays correct for what it means — when the post was published — which is what the timeline, the relative timestamp and the ActivityPub `published` show. Don't read the history as "the two used to be equal" either: they already diverged for a merged multi-device activity whose primary file is not its earliest, for a file with no parsed start time, and for the streamless Strava fallback note, which never reaches `importFitnessFiles` at all. See **Fitness Activity Dates** in `AGENTS.md`.
- **Orange TEXT uses `text-primary-text`, not `text-primary`.** `--primary` is the accent orange for **icons and fills**; as a foreground it is 3.37:1 on the card, under the WCAG AA floor for body text. `--primary-text` is the same hue tuned per theme to clear 4.5:1 on every surface such text sits on — including the `--muted` row hover — which means _darker_ in light mode and _lighter_ in dark, because on the dark ramp contrast comes from going up. This is the split the design system makes itself (`GK_ORANGE` vs `GK_ORANGE_TEXT`). Nothing catches a wrong one automatically: `app/globals.contrast.test.ts` guards the token **values**, never their usage, so a stray `text-primary` on a text node passes lint, build and the whole suite. Move stale ones over when you touch them. See **Fitness Gear** in `AGENTS.md`.
- **Tailwind v4: a bare CSS variable in an arbitrary value uses parentheses, `w-(--radix-dropdown-menu-trigger-width)`, never the v3 bracket form `w-[--radix-…]`.** v4 removed the bracket shorthand and now compiles it literally to an invalid declaration, which the browser drops — with no error and no build warning, so the element silently falls back to its default sizing. This shipped in both section-nav dropdowns at once, rendering each menu narrower than its own trigger. Guarded by `lib/components/tailwindCssVariableSyntax.test.ts`. `[var(--x)]`, `[&_svg]` and `[calc(var(--x)-1px)]` all stay valid. See **Tailwind CSS variables** in `AGENTS.md`.
