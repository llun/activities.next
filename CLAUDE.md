# Claude Code – activities.next

**Always read `AGENTS.md` at the start of any task** and follow it for all project rules. If `AGENTS.override.md` is also present in the checkout, read it as well — it takes precedence over `AGENTS.md` wherever the two conflict. Treat `AGENTS.override.md` as a layer applied on top of `AGENTS.md`, not a full replacement.

## Key reminders for this machine

- Always use **Node.js 24** for all node/yarn commands.
- Always use **`yarn`** for package management. Never use `npm install` or any other `npm` commands.
- Always create a **new branch** for changes; commit to that branch.
- **`docs/` is for durable, general-purpose reference documentation only.** Do **NOT** add implementation plans, design docs, task/PR-specific writeups, gap analyses, before/after screenshots, or any other artifact tied to a single change or PR. Keep that content in the PR description or issue tracker, not the repo. Don't create `docs/plans/`, `docs/specs/`, `docs/pr-screenshots/`, or similar scratch directories. See `AGENTS.md`.
- Treat `ACTIVITIES_*`, `OTEL_EXPORTER_*`, secrets, and host/database/storage/auth settings as runtime-only deployment config. Do not read them in `next.config.ts` or other build-time Next config; builds must work without real deployment environment variables.
- Keep `next.config.ts` as a thin Next configuration entrypoint. Do not define reusable utility functions, parsing helpers, or shared constants there; move helper logic into an appropriate `lib/` module and import it.
- Do not read `ACTIVITIES_*` or `OTEL_EXPORTER_*` variables directly, and do not define environment variable name constants, outside `lib/config/`. Add or reuse a config utility and import that instead.
- Before committing, run in order:
  1. `yarn run prettier --write .`
  2. `yarn lint`
  3. `yarn build`
  4. `yarn test`
- Start the local dev server with `yarn dev` unless a checkout-specific override says otherwise. The package script binds Next.js to `0.0.0.0`, so only run it on trusted local networks.
- Use the browser to verify any UI changes.
- Every top-level page in the `(timeline)` group shares **one** desktop content width: the layout wrapper and `PageHeader` both center at `max-w-content` (a single `--container-content: 940px` token in `app/globals.css`). Do **not** reintroduce the old two-tier `max-w-2xl`/`max-w-4xl` split, a `contentWidth` prop, or the `data-layout-width="wide"` opt-in — sections and Messages inherit the unified width.
- The **design system is the source of truth** for page chrome. Settings-style sections (settings, fitness, **admin**) lead with a **shared section header in the full-width sticky chrome** (`<PageHeader title="Settings" … />` rendered **outside** `PageHeaderSectionProvider`), then a **dropdown sub-navigation on every breakpoint — desktop included** (outline trigger with the active tab's `text-primary` Lucide icon + sentence-case label + chevron, `w-full` on mobile and `sm:w-64` from `sm` up), with each page's own title rendered in **section mode** below. **Do NOT reintroduce a vertical icon nav rail** on desktop for these sub-pages — the rail was removed in favor of the dropdown so the content always spans the full width. No horizontal tabs inside the page header either. Admin uses this same dropdown sub-nav (it previously kept a sticky-header tab strip via `PageSubnavProvider`; that was replaced to match the design system). See the **Page Header & Sub-Navigation** section in `AGENTS.md`.
- Creating **test/mock users** for local verification is allowed, but **only against a local database** — never against a remote/shared/production database (e.g. `34.79.77.243` or any non-local `ACTIVITIES_DATABASE_PG_HOST`). For local UI/browser testing, use a throwaway **SQLite** `dev.sqlite3` on `localhost` (or the docker-compose **PostgreSQL at `activities.local`**) with the sanctioned `scripts/mock/createMockUser.ts` + `scripts/mock/createMockStatuses.ts`, as documented under **"Local Manual / Browser Testing (SQLite + mock data)"** in `AGENTS.md`. Before migrating, starting the dev server, or creating users, confirm `ACTIVITIES_DATABASE` / `ACTIVITIES_DATABASE_PG_HOST` resolves to a local target. In a git worktree, do not reuse the main checkout's `.env.local` if it points at a remote DB — write a worktree-local SQLite config instead.

- **There are TWO committed reference schema dumps — use the right one per backend, and any PR that adds/edits/removes a migration MUST regenerate BOTH in the same PR.** `migrations/schema.sql` is the **PostgreSQL** dump; `migrations/schema.sqlite.sql` is the **SQLite** dump (SQLite is what local dev and the Vitest tests use). The dialects differ (`character varying`/`jsonb`/`timestamp with time zone` vs `varchar`/`json`/`datetime`), so a PG dump can't load into SQLite — read the file matching the backend. The app runs Knex migrations, but the Vitest suite builds its test databases straight from these dumps (`lib/database/testUtils.ts`), so drift breaks or falsifies tests. Regenerate by running all migrations against a **local** DB of each type: Postgres → `pg_dump --schema-only --no-owner --no-privileges` then strip pg_dump chatter (`\restrict`/`\unrestrict`, `-- …` comments, `SET default_tablespace`/`default_table_access_method`); SQLite → `sqlite3 file .schema` then strip auto-managed internal tables (`sqlite_sequence`, FTS5 `*_fts_data/idx/docsize/config` shadow tables) while keeping the `CREATE VIRTUAL TABLE … fts5` + triggers. Both files are kept tracked via `!` negations in `.gitignore` (which otherwise ignores `*.sql`). Don't hand-edit or chase old formatting; commit as `none:` if it's the only change. Full steps in the **"Keeping the reference schema dumps in sync"** subsection of `AGENTS.md`.
- **Update the docs in the same PR whenever a change makes them stale.** If you add/rename/remove commands, env vars, API routes, scripts, tooling, or conventions, grep `*.md` and `docs/` for the old names and update `AGENTS.md` / `README.md` / `CONTRIBUTING.md` / `REVIEW.md` / `docs/*` to match. See **Documentation Maintenance** in `AGENTS.md`.
- For major changes: commit → push → open PR to `main`.
- **After a PR is ready — and every time an agent changes it afterward — run the sub-agent code-review loop:** fan out sub-agents to review the whole diff, post every finding as an inline PR comment, then address → reply → resolve each thread in rounds until a clean round yields no new issues or you hit **20 rounds max**. **No external review bot currently runs on PRs (the `gemini-code-assist` bot was removed), so do NOT post `/gemini review` or wait on a bot** — the sub-agent rounds are the whole review. Full workflow in `AGENTS.md` → **Code Review Loop (Sub-Agents)**.
- **Do NOT put production or operational SQL in PR descriptions** (or anywhere committed in the repo). One-off prod DB mutations — hotfix `UPDATE`/`INSERT`/`DELETE`, data backfills, copy-pasteable runbooks — don't belong in the PR body. Describe the needed operational change in prose and hand off the actual SQL via the deployment runbook or a private ops channel. Schema changes (Knex migrations) and the committed reference schema dumps (`migrations/schema.sql`, `migrations/schema.sqlite.sql`) live under `migrations/` only (illustrative SQL in the `docs/` setup/maintenance guides is fine). This is about operational/runbook SQL — application query code such as `knex.raw`/`whereRaw` in `lib/` is unaffected. See `AGENTS.md` → Commit & Pull Request Guidelines.
- Every commit message must start with a conventional commit prefix: `fix:`, `feat:`, `chore:`, `refactor:`, `test:`, `docs:`, etc.
- Use `none:` to mark a commit as no-release, `major:` for breaking changes, and `minor:` for new backwards-compatible features. `.github/`-only commits are also treated as no-bump unless they explicitly use `major:` or `minor:`. See `AGENTS.md` for the full version bump guide.
- **For `minor` or `major` version bumps, the PR title MUST start with `minor:` or `major:`.** PRs are squash-merged, so the PR title becomes the commit subject on `main` and drives the version-bump workflow. Individual commit prefixes in the body are also scanned as a fallback, but setting the PR title is the most reliable approach.
- **Do NOT** manually change the `version` in `package.json`. A CI workflow handles version bumps automatically based on commit prefixes.
- **Test names use plain descriptive text — no `#`/`.` prefix.** Write `describe('getVisibility', …)`, not `describe('#getVisibility', …)`; name the function/method under test directly and write `it` names as behavior statements. For cases that differ only by input/expected value, prefer a table-driven `it.each([...])('$description', …)` over repeated near-identical `it` blocks. See `AGENTS.md` → Testing Guidelines.
- **Tests run on Vitest (`vi.*`), and to read a mocked module use `vi.importMock<T>('@/path')`, not `(await import('@/path')) as unknown as T`.** `vi.importMock` is a valid, documented Vitest API (the equivalent of the old `jest.requireMock`): it always returns the mock and is typed so no `as unknown as` cast is needed. Some review bots wrongly claim `vi.importMock` doesn't exist — don't switch to bare `await import()` on their say-so. See `AGENTS.md` → Testing Guidelines and `REVIEW.md`.
- **Server-only code must never import a runtime VALUE from a `'use client'` module** (`app/api/`, `lib/services|actions|jobs|database|config`). On the server such a module is a client reference, so a constant object read out of it comes back **empty** — and Vitest has no RSC boundary, so tests pass while production silently breaks (this took out poll creation entirely). `import type` is fine. Put shared constants in a dependency-free module both sides import (e.g. `lib/services/statuses/pollDurations.ts`). Guarded by `lib/clientModuleBoundary.test.ts`. See **Server/Client Module Boundary** in `AGENTS.md`.
- **Client authoring UI reads admin-configured limits from `useInstanceLimits()`** (`@/lib/components/instance-limits`), published once by the `(timeline)` layout — never a hardcoded constant. Covers the composer's character counter, the inline reply box, the poll editor, and the media/avatar pickers. Add a field to the context instead of threading a prop, and never import `lib/config/serverSettings` into a Client Component **for its value exports** (it carries `process.env` closures) — `import type` from it is fine and several admin forms do exactly that. Limits are still enforced server-side. See **Instance Limits in Client Components** in `AGENTS.md`.
- **Never call `fetch()` directly in React components.** All client-side API calls must be added to `lib/client.ts` as named exported functions and imported from there.
- **A `<Link>` rendered once per feed/list row must pass `prefetch={false}`.** `<Link>` prefetches every link that enters the viewport, so in an infinite-scroll feed that is one RSC request per row, not one per page — the home timeline's two author links per post flooded production with `GET /@user@domain?_rsc=…`. Those targets are fully dynamic routes, and `/@user@domain` additionally does a WebFinger + signed actor fetch to the **remote** server for any actor this instance has not persisted, so scrolling generated outbound federation traffic. Next 16 has no global prefetch switch (`prefetch` is per-`Link`), and `false` disables hover prefetch too — that trade is intended. Navigation chrome (sidebar, mobile nav, section sub-nav, pagination) keeps prefetching; the rule is only for links whose count scales with rows on screen. See **Link prefetching in feeds** in `AGENTS.md`.
- **Log a caught error as `err: toLoggableError(error)`** (`@/lib/utils/toLoggableError`), not only as `error: err.message` — the logger's formatter reads `err.stack` to emit `stack_trace`, and a message string reports nothing actionable. And **a user-visible degradation must be persisted, not just warned about — in a signal scoped to what actually broke.** A missing route map records `fitness_files.mapError` precisely because `processingStatus: 'failed'` means "this activity is not usable" and hides it from the detail dashboard, the stat grid, the fitness overview, the profile's Fitness tab and every rollup. Grep for what reads a flag before reusing it. See **Logging Guidelines** in `AGENTS.md`.
- **An uploaded file name is untrusted input — in `lib/services/medias/` and `lib/services/fitness-files/` run it through `@/lib/services/medias/fileName` before joining, `extname`-ing, or persisting it.** `File.name` and the presigned flows' `fileName` are plain client strings; only browser multipart uploads send a bare basename. Use `sanitizeStoredFileName` for anything stored (`medias.originalFileName` and `fitness_files.fileName` are `varchar(255)`, so an unbounded name is a PostgreSQL insert failure as well as a rendering hazard), `createMediaTempFilePath` for temp paths (`join(tmpdir(), randomHex + file.name)` escaped `tmpdir()` given three or more `..`, and with fewer produced a predictable path that defeated the random prefix) — though a temp path should now prefer a **server-derived** name over a sanitized supplied one, which is what `extractVideoPreviewFrame` (`lib/services/medias/videoPreview.ts`, the one production caller) passes it: ffmpeg picks its demuxer from the path as well as the bytes, so a valid mp4 uploaded as `IMG_%04d.jpg` made it hunt for a numbered image sequence and 500 — and `getStoredMediaExtension(contentType, fileName)` so a generated path's suffix comes from the validated content type rather than the name — `extname('clip.mp4/../../evil.html')` is `.html`, which the local driver served as `text/html`. Every `ACCEPTED_FILE_TYPES` entry must have a mapping in `EXTENSION_BY_CONTENT_TYPE`. A video's preview frame is extracted through the shared `extractVideoPreviewFrame` **before** the video is stored, never from the stored file — extracting afterwards orphaned the bytes with no `medias` row on every ffmpeg failure — and the container is validated from the ffprobe result first, so an audio-only mp4 stays a 422 that never spawns ffmpeg. In fitness-files, `getFitnessFileType` deliberately still reads the **raw** name — the 200-byte cap can truncate a long name past its extension, and it throws when neither the name nor the MIME type identifies a type. See **Uploaded file names are untrusted input** in `AGENTS.md`.
- **Fitness gear distance is DERIVED, never stored.** `fitness_gears` / `fitness_gear_components` have no distance column: a gear total is `SUM(fitness_files.totalDistanceMeters) WHERE gearId = ?` and a component total is that sum restricted to its `[addedAt, removedAt)` install window (null `addedAt` = since the gear's beginning, null `removedAt` = still fitted). Don't add a cached total — it would need reconciling on every back-dated upload, re-import, edit and delete. Both rollups reuse the same `deletedAt IS NULL` + `processingStatus 'completed'` + `isPrimary` predicate as `getFitnessActivitySummary` so the numbers agree with the fitness overview, and both answer a whole page in ONE grouped query (the component one keeps the window in the JOIN condition so an empty window still yields a 0 row). `fitness_files.gearId` deliberately has no DB-level FK (SQLite `alterTable` can't add one without a table rebuild) — ownership lives in `lib/database/sql/fitnessGear.ts`. Match sports via `normalizeActivityTypeToSportKey` (`@/lib/services/fitness-files/sportTypes`), never the raw free-form `activityType`; returning null beats guessing. A sport belongs to at most one of an actor's gears (retired included). Retired gear is out of pickers/auto-assign but stays explicitly assignable. **Imports never read Strava's gear and never create a gear row** — no `activity.gear_id`, no archive gear CSVs, no `stravaGearId` column; an imported activity is attributed from the owner's `defaultSports` mapping like any upload, editable both on each gear's form and in the Strava page's **Default gear** section (a view over `defaultSports`, not its own table). Import jobs use `assignFitnessFileGearIfUnset` (its `whereNull` guard is correctness, not optimisation — jobs re-run); only the owner's PATCH overwrites. Service reminders evaluate on write, not on a schedule (no recurring-job infra exists). **A recording device is a THIRD kind** (`kind: 'device'`) that shares almost none of this: no components, no default sports, no distance total (a head unit records rides and runs alike), no service reminder, no retiring — its page reports an activity count and a first-used date. Its identity is `fitness_gears.deviceKey` (`name:<normalized deviceName>`, else `mfr:<brand key>`, else no row), UNIQUE with `actorId` and never rewritten, while `name`/`brand`/`model`/`productUrl` are owner-editable — keying on the name would fork a duplicate the first time someone renamed "Garmin Edge 840" to "the Edge". `resolveDeviceGear` is the SOLE creator (imports call it through the best-effort `linkFitnessFileDeviceGear`; `POST /api/v1/fitness/gear` 422s a device), deleting a device RELEASES its `deviceKey` (the unique index covers soft-deleted rows) and detaches `fitness_files.deviceGearId`, and devices are filtered out of the activity gear picker **before** its kind narrowing (an unrecognised type otherwise offers all active gear). The device name links to `/fitness/gear/<id>` for the owner only; everyone else keeps the branded manufacturer link. See **Fitness Gear** in `AGENTS.md`.
- **Below 480px the gear components table snaps one data column per swipe** via `useGearTableColumns` (`@/app/(timeline)/fitness/gear/useGearTableColumns`), layered on top of the `STICKY_COLUMN` pinning that every gear table already has. It measures the table's **own** scroll container with a `ResizeObserver` rather than using a viewport breakpoint — a gear table can sit in a narrow column on a wide window — and attaches through a **callback** ref, because the table is conditional (an empty bike renders the empty state) and a ref object assigned later re-runs no effect. Under the threshold each data column takes exactly the width the pinned column leaves over, with `scroll-snap-type: x mandatory` and `scroll-padding-left` clear of the pin, so a swipe lands on a whole column. Do **not** reintroduce `min-w-[720px]`: the per-cell minimums already add up to ~724px, so it only forced the wide layout onto phones — but that also means a container between 480px and ~724px still scrolls as one block, now with the type column pinned through it. Every cell carries `wrap-anywhere`, never `break-words`: type, brand and model are free text to 255 chars, `overflow-wrap: break-word` does not reduce min-content contribution, and a column wider than its snap interval has a tail `x mandatory` can never rest on. Only the components table snaps so far; the gear list's tables pin without snapping. See **Fitness Gear** in `AGENTS.md`.
- **Navigation is customizable per account, and one registry drives every surface.** An item's id lives in `NAV_ITEM_IDS` (`lib/services/navigation/navPreferences.ts` — dependency-free, imported by both the client surfaces and the API route that validates writes) and its presentation in `NAV_ITEM_DEFINITIONS` (`lib/components/layout/nav-items.ts`); the sidebar, rail, mobile bar and the Settings → Navigation manager all derive from those, so never hardcode a nav list in a component. All of them read the single `useNavPreferences()` store that the `(timeline)` layout publishes around the chrome **and** `{children}` (the manager edits the sidebar rendered beside it). Saves send the whole preference and dedupe on the **payload**, not on what the navigation looks like — Reset stores empty lists on purpose, and keying on visible state made it a silent no-op. The sidebar's `⋯` skips hidden neighbours; the manager, which lists them, splices within the displayed list — and anything draggable must also be keyboard-reorderable. Pinned items (`LOCKED_NAV_IDS`) can never be hidden, and admin `features.*` switches only remove items from navigation: routes and APIs keep working. See **Navigation Customization** in `AGENTS.md`.
- **All inbound ActivityPub goes through JSON-LD compaction.** Run untrusted remote AP documents (notes/activities/actors) through `compactActivityPub` from `@/lib/activities/jsonld` **before** Zod validation or processing — it compacts against one canonical, **offline** context (bundled assets under `lib/activities/jsonld/contexts/`, never remote-fetched; SSRF guard) so `type` is a bare term, id refs are strings, and `to`/`cc`/`tag`/`attachment` are arrays. Every untrusted-AP entry point must compact first (shared inbox, per-user inbox, `getActorPerson`, `getActorPosts`, `getNote`). Keep the Zod schemas **liberal** — no `.strict()`, `z.looseObject` fallback for `Tag`/`Attachment`, never validate `@context` — and narrow back with `safeParse` at the consumption boundary. A new non-AS2 `type` you match on must be aliased in `CANONICAL_CONTEXT` (like `Emoji`/`Hashtag`/`PropertyValue`) with a regression test, or compaction drops it. Do **not** change `http://schema.org#` to https (Mastodon interop). Keep `jsonld` imported lazily (it breaks jsdom). See the **ActivityPub & JSON-LD** section in `AGENTS.md`.
- **Never pass `new Date()` as a prop from a Server Component to a Client Component.** Pass `Date.now()` (a `number`) instead. Client Components should accept `currentTime: number` and call `new Date(currentTime)` internally. This prevents hydration mismatches.
- **Never call `Date.now()` (or `new Date()`) during a Client Component's render** when the value feeds time-dependent output (e.g. relative timestamps in `Posts`/`Post`). The server SSR call and the client hydration call return different values and break hydration. Instead, take `currentTime: number` from the parent Server Component and forward it. This was the timeline hydration bug: `MainPageTimeline` rendered `<Posts currentTime={Date.now()} />`; the fix passes `currentTime` from `app/(timeline)/page.tsx`.
- **Every surface that shows a status post MUST render it through the shared `Posts`/`Post` components (`lib/components/posts`), and the post action set is identical everywhere.** Reply, boost, like, bookmark, react, and the `⋯` menu (quote, edit-own, delete-own, change visibility / who-can-quote; mute / block / report for others; copy link; open original) are owned by `Posts`. A signed-in page turns actions on with `currentActor` + `showActions` and **never** passes per-status action callbacks (`onReply`/`onQuote`/`onEdit`) or hides individual actions. Reply/quote/edit open one shared inline composer (`InlineStatusComposer` via the `useInlineComposer` hook) beneath the post; pages pass only optional data-sync callbacks (`onStatusCreated`/`onPostUpdated`/`onPostDeleted`/`onLikeChanged`/`onBookmarkChanged`/`onReactionsChanged`) plus `isMediaUploadEnabled`. Read-only / logged-out surfaces use `showActions={false}`. Do **not** build a bespoke post or action row. See **Status Posts & Actions** in `AGENTS.md`.
- **The reaction chips and the action row are both full-bleed (`-ml-13`), and the action row packs its actions into one `gap-1` cluster at the post's left edge with only the `⋯` menu pushed right by an `ml-auto` on its wrapper** — the auto margin is what does the work (flexbox feeds free space to auto margins **before** `justify-content` sees it, so it beats any `justify-content` the row might carry — the design kit's own row keeps an inert `justify-between` beside it). Drop the margin and `⋯` collapses into the cluster; put `justify-between` on the row without it and all five actions spread across the whole width, reading as five unrelated controls. Each row owns a separate `fullBleed` prop and they default **differently** — `Actions` pulls unless a caller opts out, `ReactionRow` pulls only when asked — and a surface with no avatar column to pull back over ends up with neither (the fitness activity detail's card passes `fullBleed={false}` to `Actions` and simply leaves `ReactionRow`'s own prop unset). The row still spans the **full** width — not for the spacing between actions, which is a width-independent `gap-1`, but so `⋯` lands on the post's right edge and the edit-history panel has that edge to line up with — so never seat it beside something else. The edit-history panel is anchored to the **row** (its trigger's wrapper is deliberately not `relative`) and sits `right-0`, flush with the post's right edge; anchored to the trigger, its 25rem width starts wherever the engagement counts push that trigger and the post's card clips the overhang. The picker trigger lives **in the action row** (`ReactionButton`, `SmilePlus` + total), not beside the chips; both halves share one `useReactionState`. A post narrower than 400px (measured with a `ResizeObserver` on the row, not a viewport breakpoint) moves bookmark and react into the `⋯` menu. **Even a bespoke presentation renders the shared `<Actions>`** — `FitnessStatusDetail` lays out its own card and places the chip row by hand, but its action row is `<Actions>`, not a local copy. See **Status Posts & Actions** in `AGENTS.md`.
- **Three fitness stat strips render through `FitnessStatGrid` (`@/lib/components/fitness/FitnessStatGrid`), and its column rule is a CONTAINER query, not a viewport breakpoint** — the activity detail page's header strip, the strip under its route map, and the inline chip in a timeline post. The gear detail page's strip (still on a `sm:` viewport query) and the fitness overview's totals (`@2xl/fitness`) are **not** migrated yet, so don't read the rule as describing the whole tree. `detail` is 1-up → 2-up at 420px → 4-up at 780px; `chip` is 2-up → 4-up at 424px and never drops to one column. The design system measures each grid's own width for the same reason `useCompactActionBar` does — a strip can sit in a narrow column on a wide window — and the old `sm:grid-cols-4` is exactly what kept four `text-[28px]` tiles in a 565px tablet column, wrapping "31.1 km/h" onto two lines. The detail page's two strips measure separately (the header one is inside the card's `p-5`, 42px narrower) and may differ by one step; that is the rule working. `@container` goes on a wrapper, never on the grid itself. Gear rides inline in the header's metadata line (`date · visibility · gear`) on the detail page and inside the distance cell ("42.6 km · Moots") in the chip. See **Fitness Stat Strips** and **Fitness Gear** in `AGENTS.md`.
- **Orange TEXT uses `text-primary-text`, not `text-primary`.** `--primary` is the accent orange for **icons and fills**; as a foreground it is 3.37:1 on the card, under the WCAG AA floor for body text. `--primary-text` is the same hue tuned per theme to clear 4.5:1 on every surface such text sits on — including the `--muted` row hover — which means _darker_ in light mode and _lighter_ in dark, because on the dark ramp contrast comes from going up. This is the split the design system makes itself (`GK_ORANGE` vs `GK_ORANGE_TEXT`). Nothing catches a wrong one automatically: `app/globals.contrast.test.ts` guards the token **values**, never their usage, so a stray `text-primary` on a text node passes lint, build and the whole suite. Move stale ones over when you touch them. See **Fitness Gear** in `AGENTS.md`.
- **Tailwind v4: a bare CSS variable in an arbitrary value uses parentheses, `w-(--radix-dropdown-menu-trigger-width)`, never the v3 bracket form `w-[--radix-…]`.** v4 removed the bracket shorthand and now compiles it literally to an invalid declaration, which the browser drops — with no error and no build warning, so the element silently falls back to its default sizing. This shipped in both section-nav dropdowns at once, rendering each menu narrower than its own trigger. Guarded by `lib/components/tailwindCssVariableSyntax.test.ts`. `[var(--x)]`, `[&_svg]` and `[calc(var(--x)-1px)]` all stay valid. See **Tailwind CSS variables** in `AGENTS.md`.
